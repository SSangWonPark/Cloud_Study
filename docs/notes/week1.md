## 1. 온프레미스 역할 → 클라우드 역할, 무엇이 바뀌는가

온프레미스에서는 "물리 자원을 누가 설계/설치/유지보수하는가"로 역할이 나뉘지만, 클라우드에서는 "가상 자원을 누가 설계하고, 누가 코드로 자동화하는가"로 역할이 재편된다. 같은 책임(아키텍처, 운영, 보안, 데이터)이 없어지는 게 아니라, 수행 방식이 수동 유지보수에서 코드/템플릿 기반 자동화로 옮겨간다.

| 온프레미스 역할 | 핵심 업무 | 클라우드에서 가장 가까운 역할 | 바뀌는 지점 |
|---|---|---|---|
| 아키텍트(엔터프라이즈/애플리케이션/스토리지/네트워크/보안) | 요구사항에 따라 IT 아키텍처 설계 | 클라우드 엔터프라이즈/애플리케이션/인프라/보안 아키텍트 | 물리 자원 설계 → 가상·코드화된 자원 설계 |
| 시스템 관리자(sysadmin) | 서버 설치, 패치, 백업/복구, 사용자 관리 | 클라우드 운영 엔지니어(관리) | 하드웨어 유지보수 → 가상 인프라 템플릿·태깅 관리 |
| 애플리케이션 관리자 | 애플리케이션 설치/튜닝/문제해결 | 애플리케이션 개발자 + DevOps 엔지니어 | 수동 운영 → 자동화된 배포·모니터링 파이프라인 |
| DBA | DB 설계/유지보수/정책 수립 | (운영 DBA 성격은) 클라우드 운영 엔지니어, (데이터 거버넌스는) 데이터 관리자 역할로 분산 | 일부 업무가 관리형 DB 서비스로 이전 |
| 네트워크 관리자 | LAN/WAN 설계·설치·확장 | 클라우드 인프라 아키텍트 + 운영 엔지니어 | 물리 장비 구성 → VPC 등 가상 네트워크 코드화 |
| 스토리지 관리자 | 스토리지 프로비저닝, 백업/복구 관리 | 클라우드 인프라 아키텍트/운영 엔지니어 | 디스크·테이프 직접 관리 → S3/EBS 같은 서비스형 스토리지 |
| 보안 관리자 | 보안 정책 구현, 취약점/침투 테스트 | 클라우드 보안 아키텍트 + 보안 운영 엔지니어 | 정책 수립 방식은 유사, 대상이 가상 자원·IAM으로 이동 |

## 2. 클라우드의 4대 책임 영역

AWS 클라우드 환경에서 비즈니스를 운영하는 책임은 크게 4개 영역으로 나뉜다.

- **비즈니스 관리**: 클라우드 엔터프라이즈 아키텍트(전체 아키텍처 총괄, 기술 CIO에게 보고), 프로그램 관리자(운영 전반 관리, 클라우드 지표/서비스 보고 관리), 재무 관리자(비용 코딩·배분·최적화 — 예: EC2 예약/스팟/온디맨드 선택 가이드)
- **인프라**: 클라우드 인프라 아키텍트(솔루션 종속 인프라 아키텍처 설계), 클라우드 운영 엔지니어 — *관리*(가상 인프라·템플릿 구축/패치) 및 *지원*(모니터링, 인시던트 대응, SLA 준수 확인)
- **보안**: 클라우드 보안 아키텍트(보안 요구사항 지정, 정책/인시던트 대응 계획 설계), 보안 운영 엔지니어(보안 구성 관리·모니터링·적용, 취약성 테스트)
- **애플리케이션**: 애플리케이션 아키텍트(클라우드 최적화 설계), 애플리케이션 개발자(코드 개발·배포 관리), DevOps 엔지니어(빌드/배포 파이프라인 자동화, IaC 구현)

이 네 영역은 **클라우드 Center of Excellence(CoE)** — 클라우드 비즈니스 오피스 + 플랫폼 공유 서비스(EC2/S3/Lambda 등) + 플랫폼 관리 서비스(CloudWatch/CloudTrail/VPC/IAM 등) + 조직 공통 서비스(AD/DNS/NTP) — 를 중심으로 맞물려 돌아간다.

## 3. Infrastructure as Code (IaC)

**정의**: 버전 관리, 지속적 통합/배포(CI/CD) 같은 소프트웨어 개발 기법을 그대로 인프라에 적용해서, 인프라를 코드로 제공·관리하는 방식.

**수동 관리 vs IaC**
- 수동: AWS 관리 콘솔·CLI·API로 직접 구성 — 빠르지만 추적/재현이 안 됨
- IaC: 소스 제어 시스템(git)에 저장된 템플릿(예: AWS CloudFormation, Terraform)으로 자동화 — 변경 이력 추적 가능, 예측 가능한 방식으로 업데이트

**이점**: 재사용성, 유지보수성, 확장성, 테스트 가능성 + 보안 모범사례를 코드에 내재화하기 쉬움 + 설계를 빠르게 반복할 수 있어 민첩성 확보 + 인프라 코드와 애플리케이션 코드를 같은 소스로 관리해 효율 향상

→ 지금 이 저장소에서 Terraform을 쓰기로 한 이유가 바로 이 IaC 개념 그 자체.

## 4. DevOps 모델에서 Dev/Ops 경계

- **Dev 흐름**: 애플리케이션 아키텍처 설계 → 코드 작성 → 빌드/컴파일 → 테스트 → 패키징
- **Ops 흐름**: 인프라 아키텍처 설계 → 인프라 코드 빌드/관리 → 워크플로 구축 → 이미지 검증 → 배포 자동화
- 각 역할(엔터프라이즈/애플리케이션/인프라/보안 아키텍트, 개발자, 운영/보안 엔지니어, DevOps 엔지니어)이 이 흐름의 각 단계를 나눠서 맡는다.
- **경계를 어디에 둘지는 정답이 없음**: 경계를 상단(수동 통제)에 두면 세밀한 제어는 가능하지만 자동화가 거의 없고, 경계를 하단으로 내릴수록(코드로 애플리케이션·OS·인프라까지 자동화) 온전한 DevOps 환경에 가까워짐. 보안 요구사항, 조직 문화, 팀 역량, 비즈니스 목표에 따라 회사마다 다르게 결정.

## 핵심 요약

- 온프레미스의 역할들은 클라우드에서 사라지는 게 아니라, "코드/템플릿을 통해 자동화하는 역할"로 재편된다.
- 클라우드 책임은 비즈니스 관리·인프라·보안·애플리케이션 4개 영역으로 나뉘고, 이들은 CoE를 중심으로 공유 서비스를 주고받는다.
- IaC는 인프라를 소프트웨어처럼 버전관리·테스트·재사용할 수 있게 해주는 핵심 개념이고, 이번 로드맵에서 Terraform을 쓰는 이유의 근거가 된다.
- Dev/Ops 경계는 조직마다 다르며, 자동화 수준은 "선택"의 문제다.
